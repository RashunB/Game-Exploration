## Instruction vs enforcement

Most of this PR is instructions, which Claude follows but nothing guarantees. Only these are enforced:

| Rule | Enforced by |
| --- | --- |
| No third-party files under `Content/` in a commit | `Tools/githooks/pre-commit`, `.claude/hooks/guard-commit.sh`, CI `content` check |
| No force-add under `Content/` by Claude | `.claude/hooks/guard-commit.sh` |
| Binary assets go through LFS, nothing over 1 MiB outside it | CI `lfs` and `size` checks |
| Manifest entries are complete | CI `manifest` check |
| Tutor writes only under `docs/learning/` | `.claude/hooks/tutor-write-guard.sh` |
| Checkpoint before MCP | warning only (`.claude/hooks/mcp-checkpoint.sh`) |
| Everything else (TDD scope, no worktrees, precedence, approvals, PR-only merges) | instructions in `AGENTS.md` and `CLAUDE.md`; PR-only becomes enforced once `main` is protected |

## Stop 2: the license-boundary logic

Files: `Tools/githooks/check-staged-content.sh:10` to `:24`; `.github/scripts/repo_checks.py:43`, `:87`, `:94`, `:123`, `:140`, `:169`; `.github/scripts/test_repo_checks.py:30`, `:51` to `:131`.

- `check-staged-content.sh` checks the index, not the working tree. Line 10 lists the staged paths under `Content/` (added, copied, modified, renamed, type-changed; deletions stay allowed so a stray file can be removed). Line 11 drops the three first-party folders. Anything left is blocked. A path that git quotes (unusual characters) fails the prefix match and is blocked: the check fails safe. Lines 22 to 24 print a reminder when level files are staged, since `vendor_content.py verify` needs the Windows staging project and can't run from a hook.
- `repo_checks.py` is what CI runs, on everything tracked:
  - `first_party` (`:43`) imports `FIRST_PARTY` from `Tools/VendorContent/vendor_content.py`, so CI and the vendor tool share one folder list. The shell check still has its own copy; its header comment says to keep them in sync.
  - `check_lfs` (`:123`) reads blobs from git's object store, not the working tree. That's why the workflow can check out without LFS objects and still verify that every LFS-pattern file is a pointer.
  - `check_size` (`:140`) is the backstop for a binary committed under a pattern `.gitattributes` doesn't cover.
  - `check_links` (`:169`) only follows relative links and skips code blocks and the vendored skills. External links are not checked, because they make CI flaky.
- The tests build throwaway git repos. The fixture (`test_repo_checks.py:30`) sets the LFS filter to `cat` so tests decide byte for byte what gets committed, even on a machine with Git LFS installed globally (this one has it, like GitHub's runners).

Watch:

- The folder list lives in four places: `.gitignore`, `vendor_content.py`, `check-staged-content.sh`, and `guard-commit.sh`'s message. Adding a first-party folder means editing all four.
- Proof that the boundary holds: in a scratch clone, a dummy file under `Content/CitySample/` was blocked by the hook, and when committed with `--no-verify`, `repo_checks.py` failed on it.

## Stop 3: wiring and enforcement

Files: `.claude/settings.json:6` to `:47`; `.claude/hooks/lib.sh`, `guard-commit.sh:12` to `:33`, `mcp-checkpoint.sh:9` to `:16`, `session-start.sh`, `tutor-write-guard.sh:9`; `Tools/githooks/pre-commit`, `install.sh:3`, `:13`; `.github/workflows/repo-checks.yml:17` to `:38`.

- `settings.json` registers three Claude Code hooks. The Bash hook uses `if: "Bash(git commit *)"` and `if: "Bash(git add *)"` so it only runs on those commands; Claude Code splits chained commands and checks each part. The MCP matcher `mcp__.*unreal-mcp__.*` covers both the project server name and a plugin-bundled one.
- Hook scripts parse their JSON input with `sed` (`lib.sh`), because Git Bash on Windows has no `jq` and may have no Python on PATH. That's fine for the flat string fields used here.
- `guard-commit.sh` blocks in two ways: a force-add under `Content/` in any one simple command of a chain (`:12` to `:22`; the per-command split was a review fix, since `git add x && rm -f y` used to be blocked), and a commit whose index fails the shared check (`:25`). It exits 2 to block, and its stderr becomes the reason Claude sees.
- `mcp-checkpoint.sh` warns once per session (a marker file in `.git/` keyed by session id) when `Content/` or `Config/` is dirty. Once per session because the first MCP write makes the tree dirty, and warning on every call after that would be noise.
- `session-start.sh` sets `core.hooksPath` only when it is unset at every scope. A global hooksPath is someone's deliberate setup, so it leaves that alone and says the Content guard is off (also a review fix).
- `Tools/githooks/install.sh:3` explains the main trap: `core.hooksPath` replaces `.git/hooks` entirely, including Git LFS's hooks. Without LFS's `pre-push`, a push sends pointer files without their objects and the remote ends up with assets nobody can download. That's why the four LFS shims live next to `pre-commit`.
- The workflow (`repo-checks.yml:17`) checks out with `lfs: false` and `GIT_LFS_SKIP_SMUDGE=1`, so CI spends none of the 10 GiB a month of LFS bandwidth. `actions/checkout` is pinned by commit, and `persist-credentials: false` keeps the token out of the checkout.

Watch:

- The Claude hook matches command text, so a command run from a script file gets past it. The git pre-commit hook and CI are the real backstops. The MCP matcher and the Windows behavior of all four hooks are unverified until `docs/windows-checklist.md` is worked through.
- `guard-commit.sh` misses `git -C <dir> commit` (the `-C` argument breaks the match). The git hook still catches it.
